# Trust & Evidence Standard

This public profile is built around a simple rule:

> **Evidence before assertion.**

## What clients can expect

### Clear evidence classes
Technical statements are separated into:
- observed evidence;
- verified result;
- inference;
- hypothesis;
- unknown.

A development result is not presented as production proof. A public benchmark result is not presented as universal generalization. A reproducible artifact is not assumed to guarantee an identical stochastic outcome.

### Minimal justified change
The default engineering question is not "what can we rebuild?"

It is:

> **What is the smallest defensible change that can produce the required measurable value?**

### Negative results are retained
Failed hypotheses, regressions, and non-transferring improvements are useful evidence. They prevent repeated cost and reduce false confidence.

### Reproducibility and provenance
Where appropriate, important claims are bound to source identity, configuration, test evidence, or an explicit authority record.

### Bounded claims
Every serious diagnostic should state both:
- what the evidence supports;
- what the evidence does **not** establish.

## Client confidentiality

Client material is private by default.

Public GitHub issues are used only for high-level project intake. Clients should never post:
- credentials or API keys;
- proprietary source code;
- private datasets;
- personal or customer data;
- trade secrets;
- unpublished sensitive research;
- internal infrastructure details.

Sensitive work should move to an agreed private channel before technical evidence is exchanged.

## Intellectual-property boundary

Public case studies are built from information that is already public or explicitly approved for disclosure.

Private implementation methods, unrelated reusable engineering infrastructure, customer assets, and confidential project details are not published merely to demonstrate competence.

## Third-party attribution

Inherited code, models, methods, datasets, and frameworks are credited to their original authors and remain subject to their original licenses and terms.

Public evidence is not used to imply authorship of work created by others.

## Engagement standard

A strong engagement should produce a decision, not just activity.

Typical outputs include:
- a failure map;
- evidence-linked hypotheses;
- a minimal experiment or verification plan;
- a repair or no-change recommendation;
- regression boundaries;
- a clear claim ceiling.

The objective is measurable technical and economic value with the least unnecessary complexity.
